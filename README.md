# Activity Pulse — فاز ۱

## نصب
1. پوشه `activity_pulse` رو داخل مسیر addons سرور اودو کپی کنید.
2. سرور رو با فلگ `-u activity_pulse` ری‌استارت کنید یا از منوی Apps → Update Apps List → جستجوی «Activity Pulse» → نصب.
3. وارد صفحه اصلی (Home Menu) بشید.

## اگر ویجت نمایش داده نشد
این تنها نقطه‌ای از کد هست که به نسخه دقیق نصب شما (Enterprise/ ساختار DOM) وابسته‌ست:
- فایل: `static/src/xml/home_menu_patch.xml`
- فایل: `static/src/js/home_menu_patch.js`

با دکمه F12 مرورگر، تب Console رو باز کنید، اگه ارور مربوط به `HomeMenu` یا `web_enterprise` دیدید،
عین همون پیام رو برام بفرستید تا مسیر importِ کامپوننت یا selector مربوطه رو دقیق تنظیم کنم.

## چیزی که این نسخه انجام می‌ده
- ساعت و تاریخ شمسی زنده (محاسبه ریاضی مستقل، بدون کتابخانه بیرونی)
- لیست اکتیویتی‌های باز کاربر جاری با رنگ‌بندی قرمز/زرد/سبز
- نمایش تعداد روزهای تاخیر برای موارد Overdue
- کلیک روی هر ردیف → باز شدن رکورد مبدأ
- دکمه «انجام شد» → دیالوگ دریافت بازخورد → ثبت از طریق متد بومی `action_feedback`

## فاز ۲ — پنل مدیریتی (این نسخه)
یک اپلیکیشن جدید با نام «پایش اکتیویتی» به منوی اصلی اضافه می‌شه.

- **کاربران عادی:** مستقیم لیست اکتیویتی‌های خودشون رو می‌بینن (بدون گرید کارمندان).
- **مدیران:** باید عضو گروه **«مدیر پایش اکتیویتی»** بشن. بعدش وارد پنل که بشن، یه گرید از
  باکس‌های کارمندانشون رو می‌بینن (اسم + تعداد قرمز/زرد/سبز). با کلیک روی هر باکس، وارد
  جزئیات اکتیویتی‌های همون کارمند می‌شن.
- **در صفحه جزئیات هر کارمند:**
  - ویرایش سریع موعد هر اکتیویتی (فیلد تاریخ، بدون نیاز به باز کردن رکورد اصلی)
  - دکمه «پیگیری»: یک پیام خودکار برای کاربر مسئول در Discuss (اینباکس پیام‌هاش) ارسال
    می‌کنه که ازش می‌خواد وضعیت رو گزارش بده
  - دکمه «پیامک»: فعلاً فقط یک اعلان «به‌زودی» نشون می‌ده؛ در فاز ۳ به کاوه‌نگار وصل می‌شه
  - دکمه «انجام شد»: همون منطق فاز ۱ (بازخورد اجباری)
  - کلیک روی متن هر اکتیویتی (نه دکمه‌ها) → باز شدن مستقیم رکورد مبدأ

### رفع مشکل «ادمین همه اکتیویتی‌ها رو نمی‌بینه»
گروه «مدیر پایش اکتیویتی» به‌صورت پیش‌فرض به هیچ‌کس داده نمی‌شه؛ برای اینکه از همون ابتدا
قابل تست باشه، این نسخه به‌طور خودکار کاربر Administrator رو عضو این گروه می‌کنه. برای هر
مدیر دیگه، این مسیر رو برید:
Settings → Users & Companies → Users → کاربر موردنظر → تب Access Rights →
بخش «Productivity» → تیک «مدیر پایش اکتیویتی».

### نکته فنی مهم درباره امنیت
همه‌چیز از طریق متدهای اختصاصی روی خودِ `mail.activity` پیاده شده (نه یک مدل واسط)،
و کنترل دسترسی (مدیر / غیرمدیر) داخل خودِ متدها چک می‌شه — هیچ `ir.rule` سراسری
روی `mail.activity` تغییر نکرده، پس رفتار بقیه بخش‌های اودو (چت‌تر، کانبان‌ها، منوی
Activities بالای صفحه) دست‌نخورده می‌مونه.

بعد از نصب/آپدیت این فاز، حتماً یک بار دستور زیر رو بزنید:
```bash
sudo systemctl stop odoo
/usr/bin/odoo --config /etc/odoo/odoo.conf -d AirexOdoo -u activity_pulse --stop-after-init
sudo systemctl start odoo
```

## فاز ۳ — اتصال پیامکی کاوه‌نگار (این نسخه)

### تنظیم کلید API
1. وارد Settings اودو بشید (دولوپر مود لازم نیست).
2. توی نوار سمت راست تنظیمات، بخش **«پایش اکتیویتی»** رو پیدا کنید.
3. کلید API کاوه‌نگار و نام الگو (Template) رو وارد کنید — طبق چیزی که گفتید،
   نام الگو رو `odooactivty` بذارید (این مقدار از قبل به‌عنوان پیش‌فرض ست شده).
4. Save بزنید.

عمداً کلید API رو داخل کد ماژول قرار ندادم؛ چون این کد ممکنه بعداً جای دیگه‌ای
(مثلاً گیت) هم ذخیره بشه و بهتره کلیدهای واقعی همیشه فقط توی دیتابیس (به‌صورت
`ir.config_parameter`) بمونن، نه توی فایل‌های کد.

### نگاشت توکن‌ها
با توجه به کدی که فرستادید، فرض کردم الگوی `odooactivty` شما این‌طور استفاده می‌شه:
- `token`  → نام کاربر مسئول اکتیویتی
- `token2` → نام رکورد مرتبط (یا خلاصه اکتیویتی)
- `token3` → موعد اکتیویتی به شمسی

اگه متن الگویی که توی پنل کاوه‌نگار ساختید نگاشت متفاوتی داره (مثلاً token3 قراره
ساعت باشه نه تاریخ)، بگید تا نگاشت `action_send_sms_dashboard` رو توی
`models/mail_activity.py` دقیق تنظیم کنم.

### شماره موبایل
شماره از `partner.mobile` یا در نبودش `partner.phone` (اطلاعات تماس مرتبط با
کاربر اودو) خونده می‌شه. اگه کارمندی شماره‌ای ثبت نکرده باشه، دکمه پیامک خطای
مشخص «شماره موبایلی ثبت نشده» رو نشون می‌ده.

### نیازمندی فنی
این بخش از پکیج پایتون `requests` استفاده می‌کنه که معمولاً به‌صورت پیش‌فرض همراه
اودو نصب می‌شه. برای اطمینان:
```bash
python3 -c "import requests; print('ok')"
```
اگه خطا داد:
```bash
pip install requests --break-system-packages
```

## اصلاحات جدید: کنترل دسترسی ویرایش + تاریخچه بهره‌وری

### ۱. ویرایش/لغو اکتیویتی — این نسخه محدودیت رو سراسری کرد
با تأیید صریح شما، این محدودیت حالا فقط مخصوص پنل ما نیست — روی خودِ مدل
`mail.activity` در کل اودو اعمال شده:

- **ویرایش (write)** و **لغوِ خام بدون بازخورد (unlink مستقیم)** فقط برای
  «سازنده اکتیویتی» (`create_uid`) یا عضو گروه «مدیر پایش اکتیویتی» مجازه —
  چه از پنل ما، چه از چت‌تر یک لید CRM، چه از کانبان پروژه یا هر جای دیگه اودو.
- **«انجام شد» (تکمیل با ثبت بازخورد)** عمداً از این محدودیت مستثناست — کاربر
  مسئول همیشه می‌تونه کار خودش رو با ثبت بازخورد تموم کنه (چه با تیک سبز
  بومی اودو، چه از پنل ما). این تمایز عمدی بود: هدف جلوگیری از **فرارِ بی‌حساب**
  (جابه‌جا کردن موعد یا حذف بی‌سروصدا) بود، نه جلوگیری از تکمیل واقعی کار.

**⚠️ ریسک‌هایی که باید بعد از فعال‌سازی مراقبشون باشید:**
بعضی اتوماسیون‌ها یا فرایندهای داخلی اودو (مثلاً اتوماسیون‌هایی که با کاربر
دیگه‌ای غیر از سازنده اجرا می‌شن، یا زنجیره «Next Activity» در بعضی ماژول‌ها)
ممکنه سعی کنن اکتیویتی رو write/unlink کنن و حالا با خطای دسترسی مواجه بشن.
اگه بعد از این آپدیت جایی از سیستم خطای غیرمنتظره «Access Error» روی
اکتیویتی‌ها دیدید، به من بگید تا استثنای مشخصی براش اضافه کنم.

**راه بازگشت سریع (بدون نیاز به من):** اگه لازم شد فوری این محدودیت رو خاموش
کنید، برید به: Settings (Debug mode روشن) → Technical → Security → Record Rules
→ جستجوی «Activity Pulse: ویرایش/لغو» → رکوردهای مربوطه رو Archive/غیرفعال کنید.

### ۲. مدیر حالا همه‌ی اکتیویتی‌های سیستم رو می‌بینه (بدون محدودیت دیدِ سند)
قبلاً مدیر توی پنل فقط اکتیویتی‌هایی رو می‌دید که خودش دنبال‌کننده یا محول‌کننده‌ی
رکورد مبدأشون بود — این یک قانون بومیِ خودِ اودو روی `mail.activity` بود (نه
چیزی که ما اضافه کرده باشیم)، که می‌گه فقط کسی می‌تونه اکتیویتی رو ببینه که به
سند مرتبطش هم دسترسی داره. این اصلاح شد: توی همه‌ی متدهای پنل مدیریتی (لیست تیم،
جزئیات هر کارمند، ویرایش موعد، پیگیری، پیامک، KPI)، برای مدیر عمداً `sudo` می‌کنیم
تا این محدودیت اثر نذاره و بتونه واقعاً همه‌ی اکتیویتی‌های سیستم رو ببینه و مدیریت
کنه — حتی اکتیویتی‌هایی که کاربران دیگه برای هم گذاشتن. کنترل دسترسی همچنان کاملاً
دست خودمونه (چک `is_activity_pulse_manager()` قبل از هر `sudo`)، پس امنیت به‌هم
نمی‌خوره؛ فقط محدودیت دیدِ سند برای «مدیرِ تأییدشده» برداشته شده. برای کاربر عادی
هیچ‌چیزی تغییر نکرده.

### ۳. تاریخچه و بهره‌وری هر کارمند
داخل صفحه جزئیات هر کارمند (چه مدیر وارد بشه چه خودِ کاربر)، دکمه **«تاریخچه و
بهره‌وری»** اضافه شد. با کلیک روش:
- لیست اکتیویتی‌های **قبلاً انجام‌شده** همون کاربر رو به ترتیب زمان انجام می‌بینید
- هرکدوم مشخصه که چند روز دیرتر یا زودتر از موعد انجام شده
- بالای لیست، میانگین کلی (مثلاً «میانگین ۲.۳ روز تاخیر» یا «میانگین ۱.۵ روز زودتر
  از موعد») نمایش داده می‌شه

این تاریخچه از طریق override کردن متد بومی `action_feedback` اودو ساخته شده، یعنی
هر بار اکتیویتی‌ای در هر جای اودو (نه فقط پنل ما) «انجام‌شده» علامت بخوره، خودکار
یک رکورد تاریخچه ثبت می‌شه — پس آماری که می‌بینید کامل و واقعیه.

## فاز درخواست تمدید موعد

**مشکلی که حل می‌کنه:** گاهی یه اکتیویتی به دلیل موجه (نه تنبلی) تاخیر می‌خوره —
مثلاً منتظر تأیید مشتریه. کاربر مسئول باید بتونه رسماً درخواست زمان اضافه بده،
بدون اینکه بتونه خودسرانه موعد رو عوض کنه یا این تاخیر از چشم مدیریت پنهون بمونه.

### روند کار
1. کارمند روی دکمه‌ی **«درخواست زمان اضافه»** (فقط وقتی خودش اجازه‌ی ویرایش مستقیم
   نداره نمایش داده می‌شه) کلیک می‌کنه، تاریخ پیشنهادی و دلیلش رو می‌نویسه.
2. یک پیام خودکار توی Discuss برای **سازنده‌ی همون اکتیویتی** (نه لزوماً مدیر —
   هرکسی که اون کار رو تعریف کرده) ارسال می‌شه.
3. سازنده از دکمه‌ی **«درخواست‌های تمدید»** بالای پنل (که برای همه‌ی کاربران،
   نه فقط مدیران، در دسترسه و شمارنده‌ی درخواست‌های در انتظار رو نشون می‌ده) وارد
   لیست درخواست‌ها می‌شه و تأیید/رد می‌کنه.
4. با تأیید: موعد واقعاً به‌روزرسانی می‌شه و یه پیام هم توی چت‌تر رکورد مبدأ ثبت می‌شه.
   با رد: هیچ تغییری در موعد ایجاد نمی‌شه و به کارمند اطلاع داده می‌شه.

### چطور تاخیر واقعی گم نمی‌شه
موعد *اصلیِ* اولین‌بارِ هر اکتیویتی همیشه جداگانه ذخیره می‌شه (حتی اگه چندبار پشت
سر هم تمدید بگیره). وقتی اکتیویتی بالاخره انجام بشه:
- توی تاریخچه/KPI، «روزهای تاخیر» همیشه نسبت به همون موعد اصلی حساب می‌شه —
  نه موعد تمدیدشده — پس یه کار که واقعاً ۱۰ روز از موعد اصلی‌اش گذشته، همیشه
  به‌عنوان «۱۰ روز تاخیر» ثبت می‌مونه.
- در کنارش، یک یادداشت شفاف «X روز با دلیل Y تمدید شد» هم اضافه می‌شه، تا هم
  تاخیر واقعی دیده بشه، هم دلیل موجهش.
- حتی توی نمای زنده‌ی لیست اکتیویتی‌های باز، یه تگ بنفش «تمدیدشده» کنار اون
  اکتیویتی نشون داده می‌شه.



- ارسال خودکار پیامک/پیگیری برای اکتیویتی‌های با تاخیر زیاد (کرون شبانه)
- گزارش Excel/PDF از وضعیت تیم

## فاز تجربه کاربری + بررسی کیفیت

### تاریخ شمسی واقعی
همه‌ی فیلدهای تاریخ داخل پنل (ویرایش موعد، درخواست تمدید، رد کیفیت) حالا از یه
ورودی اختصاصی با سه دراپ‌داون روز/ماه/سال شمسی استفاده می‌کنن — نه `input type=date`
میلادیِ خام مرورگر.

### نمایش خلاصه در تاریخچه
فیلد «خلاصه» (توضیحی که کاربر موقع تعریف/انجام اکتیویتی می‌نویسه) حالا زیر اسم
رکورد در تاریخچه هم نمایش داده می‌شه، نه فقط اسم تسک/رکورد.

### فعالیت‌های لغوشده
دکمه‌ی جدید «فعالیت‌های لغوشده» کنار «تاریخچه و بهره‌وری» — لیست اکتیویتی‌هایی که
بدون ثبت انجام‌شدن، حذف/لغو شدن، همراه با اینکه چه کسی لغوشون کرده.

### بررسی کیفیت انجام کار
وقتی کاربری اکتیویتی‌اش رو «انجام شد» می‌زنه (از هرجای اودو، نه فقط پنل ما):
- **اکتیویتی فوراً تکمیل می‌شه** — هیچ‌وقت معطل تأیید کسی نمی‌مونه.
- اگه سازنده‌ی اکتیویتی با کاربر مسئولش فرق داشته باشه (یعنی خودش برای خودش
  نساخته بوده)، یک مورد «بررسی کیفیت» برای سازنده ساخته می‌شه و پیامی هم توی
  Discuss براش می‌ره.
- سازنده از دکمه‌ی **«بررسی کیفیت انجام کار»** بالای پنل (با شمارنده‌ی موارد
  در انتظار) وارد صف بررسی می‌شه:
  - **تأیید** → هیچ اتفاق خاصی نمی‌افته، فقط وضعیت ثبت می‌شه.
  - **رد** → باید دلیل رد + موعد جدید رو مشخص کنه؛ در این حالت:
    - یک اکتیویتی **جدید** با همون مشخصات (نوع، خلاصه، کاربر مسئول) و موعد
      جدید ساخته می‌شه تا کار دوباره انجام بشه.
    - رکورد تاریخچه‌ی قبلی (که کارِ اولیه توش ثبت شده بود) حذف نمی‌شه، فقط
      توی تاریخچه/بهره‌وری کاربر به‌صورت **خاکستری** با برچسب «ردشده توسط
      محول‌کننده» و دلیلش نمایش داده می‌شه — یعنی سابقه‌ی این اتفاق برای
      همیشه می‌مونه، فقط دیگه به‌عنوان یک انجامِ موفق حساب نمی‌شه.

اگه سازنده‌ی یک اکتیویتی خودِ همون کاربر مسئول باشه (یعنی خودش برای خودش
یادآوری ساخته)، اصلاً نیازی به بررسی کیفیت نیست و این مرحله رد می‌شه.

## فاز دسته‌بندی کاربران

### نمایش همه‌ی کاربران در گرید
قبلاً فقط کارمندانی که اکتیویتی باز داشتن توی گرید تیم دیده می‌شدن. الان همه‌ی
کاربران فعال (حتی با صفر اکتیویتی باز) نشون داده می‌شن.

### دسته‌بندی کاربران
مدیر از منوی **«دسته‌بندی کاربران»** (زیرمنوی اپ «پایش اکتیویتی») می‌تونه
دسته بسازه (مثلاً «فروش»، «پشتیبانی»، «تولید محتوا») و کارمندها رو بهش اضافه
کنه (یک کارمند می‌تونه توی چند دسته هم‌زمان باشه).

بالای گرید تیم، تب‌های دسته‌بندی (همه / هر دسته / بدون دسته) نشون داده می‌شه تا
مدیر راحت‌تر کارمند موردنظرش رو پیدا کنه. دکمه‌ی «مدیریت دسته‌بندی‌ها» هم مستقیم
از داخل پنل، فرم ساخت/ویرایش دسته‌ها رو باز می‌کنه.






## فاز پاکسازی خودکار صندوق پستی

وقتی درخواست تمدید یا بررسی کیفیت ساخته می‌شه، یک پیام توی Discuss برای
تصمیم‌گیرنده (سازنده/محول‌کننده) می‌ره. حالا به‌محض اینکه اون شخص تصمیمش رو
بگیره (تأیید یا رد، فرقی نداره)، همون پیام مشخص به‌صورت خودکار «خوانده‌شده»
علامت می‌خوره — یعنی صندوق پستی کاربر با موارد کهنه‌ای که کارشون قبلاً انجام
شده شلوغ نمی‌مونه. پیام‌های نتیجه‌ی تصمیم (که به درخواست‌دهنده/انجام‌دهنده
می‌ره) دست‌نخورده باقی می‌مونن، چون اون‌ها صرفاً اطلاع‌رسانی‌ان و اقدام دیگه‌ای
روشون لازم نیست.
